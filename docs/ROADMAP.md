# BA Platform Roadmap

## Branding Solution — consume Brand Creator's `.BAB` format (proposed 2026-09-01)

When productizing the Console/Portal for other clients, each deployment needs its own branding (colours, logo, typography) instead of the current hardcoded Barely Artificial styling. Per the earlier productization audit, this Console alone has ~30 hardcoded "Barely Artificial" text references and 36 hardcoded colours bypassing the CSS `:root` variables.

Per Paul's decided direction, this should **not** be a bespoke in-app theme-editor — it should import and apply a `.BAB` package (brand.json + logo/assets: colours with role + onWhite/onDark rules, typography, logo rules, UI component states, voice/tone) exported from the separate **Brand Creator** app (BAA-010). This Console/Portal becomes a **read-only consumer** of `.BAB` — no in-app brand-editing UI, ever. v1 distribution is manual (download from Brand Creator, import by hand); no auto-sync yet.

**Not yet built, gated on**: Brand Creator actually shipping a usable `.BAB` export. Groundwork that's safe to do independently: tightening the CSS custom-property architecture (fewer hardcoded colours, cleaner `:root` variables) so mapping `.BAB` fields onto this app's CSS becomes mechanical rather than a rewrite. Also still outstanding whenever templating happens: the hardcoded "Barely Artificial" text references, hardcoded Calendly links, and the `library.source` enum values baked with `"Barely Artificial"`/`"Customer"` as literal values.

Paul wants Actions available directly inside the Edit Lead and Edit Opportunity side panels too, the same way Attachments were added into the Create/Edit Opportunity dialog earlier this session.

## ~~Bug: an Action's assignee can't be changed after it's added~~ (found and fixed 2026-09-01)

`getActionItemsMarkup()` (`js/app.js`) only gave an existing action item two controls: the done checkbox and a delete button. The assignee dropdown only existed on the "Add an action" form, used once at creation — there was no way to reassign an action afterwards, including one added as "Unassigned." Affected Leads, Opportunities, and Projects equally, since all three share this one implementation.

**Fixed**: each action row now has an always-visible assignee `<select>` (pre-selected to the current assignee) that writes immediately via a new `reassignActionItem()` function on change.

## Bug: Customer "Users" count is a static, dead field (found 2026-09-01)

Paul asked what makes a customer's "Users" count go up — is it when a contact accepts a Portal invite? Checked the code: it isn't anything. `users` is set to `0` at customer creation (three separate create paths — New Customer dialog, Lead promotion, Opportunity new-customer creation) and never written to again anywhere in the app. There's no UI to edit it either. It will show 0 forever regardless of how many contacts are invited or actually log in.

Also clarified while investigating: "Send invite" doesn't wait for the contact to accept anything — clicking it immediately creates a real Firebase Auth account (`createUserWithEmailAndPassword`) and emails a password-reset link as the invite. `contact.portalAccountCreated` becomes `true` the moment the button is clicked, not when the contact actually sets a password and logs in for the first time. So even "invited" isn't quite what it sounds like today, let alone "active user."

**Fix direction, not yet decided**: make `users` reflect something real — options include a count of contacts with `portalAccountCreated: true` (invited, computed live rather than a stored field), or a genuine "has ever logged in" signal if that's trackable via Firebase Auth (would need a real last-sign-in check, more involved). Simplest fix is the former — replace the static stored field with a computed count of invited contacts, which is already the data the app has today.

Paul asked directly whether Bookings and Events were the same thing — genuine overlap existed: both pages' own descriptions listed "training sessions" and "project meetings" as things they covered. Decided to merge Bookings into Events (Console only for now, Portal's separate "Your Bookings"/"Your Events" pages untouched), migrating existing data rather than deleting it. Built same session:

- Event's Status options gained **Cancelled** (previously only Scheduled/Logged) so nothing that Bookings could express is lost — the existing "Logged"-only filters used for project time totals and the customer health flag both continue to work unchanged since Cancelled isn't Logged.

Safe to run more than once — records already migrated are skipped by checking `migratedFromBookingId` against what's already in Events. - Dashboard's separate Bookings summary card removed; Calendar page title and a couple of stray "and bookings" mentions in copy updated to match.

## Product Direction: A More Human CRM (named 2026-08-31)

Paul's own words: he wants this platform to feel **more human than other CRM systems — almost like a PA**. This isn't a new feature so much as the connective thread running through a cluster of ideas he'd already been describing individually in the run-up to naming it — worth keeping visible as a lens for evaluating *future* suggestions too, not just the ones already logged. Items already on this roadmap that serve this direction directly:

- **Customer Memory** — soft, practical "how to deal with them" facts (e.g. "never answers the phone") — the kind of thing a good PA just quietly remembers so you don't have to.
- **"Regret" button on Lost deals** — a genuine, reflective post-mortem prompt, not a data-entry chore.
- **"Where did we leave this?"** — a current-state catch-up, the exact question you'd ask an assistant walking back into a room.
- **"Morning Brief"** — narrative, personalised, judgement-carrying prose ("the proposal has been with them for 4 days and needs chasing up"), not a bullet list of raw data.
- **"Tell the Story"** — a record's history read back as plain English, not a log dump.
- The whole **AI Features via Claude API** section — customer briefings, follow-up drafting, note cleanup — all named "meaningful use, not AI for the sake of it" from the start, which is really the same instinct as this direction, just not named as such yet.

**How to apply this going forward**: when scoping or suggesting new features, the PA framing is a genuine tiebreaker — prefer the version of a feature that reads like something a thoughtful assistant would say or notice, over the version that's just a cleaner data table. Doesn't mean every feature needs prose or AI (Customer Memory and the Regret button are both plain fields, no AI involved) — it means the *tone and framing* of what the app surfaces should feel considerate and specific, not generic and mechanical.

## AI Features via Claude API (proposed 2026-08-30, approved 2026-08-30)

Paul envisages an API connection to Claude, explicitly wanting meaningful use rather than "AI for the sake of it." **A real architecture decision has to be made before any of these can ship**: the app is deliberately backend-less (browser talks straight to Firebase, no server in between). Calling the Claude API directly from the browser with an embedded API key would let anyone open dev tools and lift that key to run up usage on the account — so this needs one small, narrowly-scoped server-side proxy (a single Firebase Cloud Function or equivalent) that holds the key and forwards requests. This is a deliberate, scoped exception to the no-backend architecture, not a slippery slope.

**Proxy architecture — decided 2026-08-31, not yet built:**
- **Shape**: a single Firebase Cloud Function (`callClaude`) holding the Anthropic API key server-side. It verifies the caller's Firebase Auth token before forwarding any request — the Console/Portal never see the key.
- **Multi-tenant model**: one Function + key per client's own Firebase project, matching the existing per-client deployment model from [[project-productization-direction]] — keeps billing and data isolation clean per client, no shared multi-tenant logic needed.
- **Cost control**: a simple per-admin (or per-day) call-count cap enforced in the Function itself, backed by a Firestore counter — cheap insurance against a runaway loop or an over-eager rep, not meant to be sophisticated at v1.
- **Model choice**: cheaper/faster model (Haiku-tier) by default for short tasks (deal-risk one-liners, quick-add field extraction, note cleanup); reserve a stronger model only for the richer outputs (customer briefing, follow-up email draft) if quality demands it.
- **Response mode**: one-shot request/response everywhere at first; add streaming later only for the slower, longer outputs (customer briefing, follow-up drafting) if they feel sluggish — no need to build both modes up front.
- **Data privacy note (client-facing, not engineering)**: this goes through Anthropic's API, not consumer Claude.ai — API inputs aren't used for training by default. Since Relationship History/Notes are real customer PII, worth a line in whatever terms are given to clients; have this answer ready before it comes up in a demo.

This unblocks every feature below — smallest possible first build is the Function itself plus Firebase-Auth verification and the per-admin cap, before wiring up any individual feature.

Approved feature ideas (in rough priority order, most valuable first):

- **Customer briefing before a call** — one click on a Customer/Opportunity generates a short "here's where things stand" summary from everything already in the record: Relationship History, Notes, past Projects, Events, audit log. The most on-brand use given the fields already being added this session — the raw material already exists, just scattered across sections.
- **Follow-up email drafting** — given an Opportunity's stage, notes, and history, draft a personalised follow-up for the rep to review and send. Always a draft a human approves before sending — no autonomous sending.
- **Meeting/call note cleanup** — a rep pastes raw, messy notes from a call; Claude turns them into a structured update (key points, next steps) and can suggest a Relationship History entry.
- **Quick-add from unstructured text** — paste a business card's OCR text, an email signature, or a scrawled note, and Claude extracts structured fields (name, role, phone, email) into the dynamic-contact-list form instead of manual typing.
- **Deal risk flagging in plain English** — beyond the rule-based stalled-deal flag already proposed above, a short qualitative read: "this one looks stalled — no stage movement in 3 weeks and the close date's slipped twice."

**Deliberately excluded** (flagged as AI-for-its-own-sake, not proposed): a general chatbot/"ask anything" interface, and AI-generated dashboard commentary that just restates data already readable directly on the page.

## "Tell the Story" — plain-English audit trail narrative (proposed 2026-08-31)

Paul wants a feature on a record's detail panel that reads its full history back as a plain-English story, not a raw log list — his own example: *"This item was added as a lead on 1st June 25 by Fred Bloggs, it was then promoted to an opportunity by..."*

**Real technical prerequisite, not yet true today**: `logAuditEvent(action, entityType, entityLabel)` (`js/app.js`) only stores a human-readable label at the time of the action, never the record's actual Firestore document ID. That means there's currently no reliable way to fetch "every audit entry for *this specific* Lead" — only "every audit entry whose label happened to match this text," which breaks the moment a record is renamed, and can't distinguish two records that happen to share a name. **Tell the Story needs `logAuditEvent` extended to also capture an `entityId`** on every call site across the app (there are many — Leads, Opportunities, Customers, Projects, etc.) before this feature can be built reliably. Older audit entries logged before that change won't have an ID and would need to be excluded from the story, or matched best-effort by label as a fallback for pre-existing history.

**The genuinely interesting part — chaining across an item's whole lifecycle.** A single "item" isn't one record: it's a Lead that became an Opportunity that became a Project, three different documents with three different IDs and `entityType`s. Paul's own example spans exactly that chain. The feature needs to walk the existing lifecycle links each record already stores (`Lead.convertedOpportunityId`, `Opportunity.sourceLeadId`/`convertedProjectId`, etc.) to pull audit entries from *all* linked records, merge them into one chronological timeline, and only then render it as English.
